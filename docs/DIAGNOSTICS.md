# 连接诊断

服务器将连接生命周期事件写入标准日志。使用 systemd 的部署可查看：

```sh
journalctl -u shareserial-preview.service --since "10 minutes ago"
```

服务名取决于维护者自己的部署。事件中的 `connection` 是进程内诊断编号，重启后会重新计数，不是 Local/Remote ID，也不是认证凭据。

| 事件 | 含义 |
| --- | --- |
| `ws_open` / `ws_close` | Hub 接受或移除连接 |
| `local_shared` / `local_unshared` | 注册共享或释放 Local ID |
| `local_id_conflict` | 新连接请求的 ID 仍被其他连接占用；`owner_connection` 指向原连接 |
| `remote_write_state` | Local 更新远端写入暂停状态，记录 paused 与 write_epoch，不包含串口数据 |
| `ws_read_end` | 读取终止；记录超时分类、对端关闭码及已读取帧/字节数 |
| `ws_write_end` / `ws_ping_failed` | 数据写入或心跳发送失败 |
| `ws_send_queue_full` | 有界发送队列积压，Hub 关闭慢连接 |
| `ws_shutdown` | Hub 因服务关闭而终止连接 |

按同一进程、同一 `connection` 关联事件。移除连接会关闭 socket，所以随后的 `socket_closed` 可能是清理结果；不能把每一条读取失败都当成最初的故障。帧/字节计数针对 WebSocket 消息，包含 JSON/Base64 开销，不等于串口有效字节数。读取超时说明未及时收到 Pong，不能仅据此区分网络阻塞、浏览器暂停或对端异常。

这些 WebSocket 诊断日志不记录串口载荷、端口名称、请求头、对端自定义关闭文字或原始错误文字；HTTP/Gin 与 TLS 握手日志仍使用原有格式。日志仍包含会话 ID，维护者应控制日志访问和保留时间。部署的日志速率/容量限制可能抑制大量重复事件。

Local 和 Remote 的终端只显示串口 RX/TX。WebSocket、授权、P2P、重连等诊断事件分别放在独立的有界内存缓冲中，平时不插入串口记录；Local 和 Remote 可分别点“导出系统日志”导出最近最多 500 条事件。Local 串口导出只含 RX/TX，Remote 的“导出 RX”只含接收数据；清空串口记录不清空系统日志。RX/TX 历史仍最多 2000 条且原始字节最多 2 MiB，TX 标明来源和入队顺序。系统日志只保存在当前页面内存，页面刷新后清空；服务器自身的 WebSocket 日志按服务端日志轮转保留。

页面没有刷新也可能发生 WebSocket 重连。Local 首先尝试原 ID；若服务器返回 `local_id_in_use`，当前版本会生成新 ID 并重试，最多 5 次。只有注册确认后才显示可分享的 ID。若没有重新开关串口却发生换号，应查找 `local_id_conflict`，再对照旧连接何时 `local_unshared`；不能仅凭换号判定网络故障。

Remote 压测程序的等待超时不会自动成为 Local 的串口错误。小批量回环通过也不代表持续传输稳定；测试超时不能直接等同于数据丢失。

v3 的 Local TX 记录含本页入队序号和本机/Remote 来源；完成 write 后才计入 TX，跳过的旧队列记录原因并可能留下序号间隔。Remote TX 仅代表提交，设备 RX 无通用的请求归属。暂停远端发送保留接收和订阅，恢复不重放旧队列；区别于资源超限后整条共享连接关闭。

## 参数修改的确认与提示

串口问题先用串口 API 设置并读回驱动参数，使用已知载荷比较原始字节，再独立验证 WebSocket API 和应用处理；浏览器页面、原生 Web Serial 与权限对话框另做验证。应区分 API 返回成功、驱动读回、字节一致和界面显示，不把其中一项当作其他项的证明。

Remote 下拉框中的编辑值需点击“应用参数”才提交；编辑后显示“未应用”。“Local 已确认”单独展示最近确认的参数，等待修改结果期间不会把草稿当作生效值。Local 收到可执行的请求后记录来源和原/新参数，完成后显示持续的成功提示；拒绝、失败或恢复原参数也有提示。需要排查参数请求时，可从 Local 或 Remote 导出系统日志；这些事件不会显示在串口 RX/TX 终端。

服务器的 serial_config_requested 只证明请求已被接受，serial_config_completed 的 success 才表示 Local 回报的执行结果。没有 accepted 事件时，应先检查是否点击应用、权限和 Remote 错误提示，不能直接认定网络或串口驱动故障。Local 的确认表示打开串口的 API 已完成，不是物理线路波特率测量。

虚拟 COM 对可能直接转发字节，波特率选项是否影响传输取决于驱动及仿真设置。例如 [com0com 官方说明](https://com0com.sourceforge.net/com0com/ReadMe.txt) 将波特率仿真作为单独选项。两端速率不一致仍能交换字节，不能单独证明参数修改失效；虚拟串口测试也不能替代物理 UART 速率匹配验证。

## P2P 故障快照

P2P 异常不需要依赖仍在页面上可见的滚动日志。服务器的 `serial_p2p_failure_details` 按实际 Socket 角色，每个授权/协商轮次最多记录 Local、Remote 各一份；页面清日志或刷新不会删除已写入服务器的记录，保留时间仍由部署的日志轮转决定。

快照包含 `application_cause`（rx_send/rx_queue/tx_send/tx_queue/tx_wait/serial_frame/tx_integrity/tx_dispatch）、原生 `channel_error` 类型及 `sctp_cause` 数字码、`channel_state`、主通道 `serial_buffered`、`assessment_active` 和 `assessment_buffered`。发送积压按字节计，上限 1 MiB；`sctp_cause=-1` 表示未取得数字码。应用回退在关闭评估通道前冻结这些值，RTC 原始错误文字、串口数据、候选地址、SDP 和授权凭据不写入快照。

`primary=true` 表示服务器首先收到该端报告，不能单凭它确定两台电脑实际出错的先后。另一端会在当前授权和轮次内补报，已自行报告的端不重复发送；补报只增加诊断证据，不覆盖首个回退原因，不重置重试窗口，不重放 TX。旧轮次或失效授权的迟到报告丢弃。`application_cause=rx_send` 表示设备 RX 的直连转发失败，不等同于本机串口写入失败；原因仍需结合通道状态、测速状态和另一端快照判断。

2026-10-30 的真实反馈是在点击“评估网络”后出现通道错误。服务器留存证据为先前已建立直连，首次收到 Local 的 application 回退时 ICE/DTLS/SCTP 仍 connected，无重启或资源拒绝。旧版未保存应用入口及另一端详情，页面原始事件已丢失，因而尚未确定根因。此前的同机浏览器通过记录不能代替该异网问题的复现和验收。

## 页面网络参考

Local 和 Remote 侧栏提供“共享网络参考”。只有点击“评估网络”才开始，可取消，不会打开串口、申请远端权限或修改波特率。按钮自动跟随当前链路：未直连测服务器，已直连测所选对端的 P2P。Local 有多个已授权远端时，可在原侧栏选择对象；默认优先直连端。路径、授权或对象变化使旧结果失效，进行中的评估会取消，需手动重新评估。

### 未直连：服务器参考

每轮 6 次轻量 HTTP 探测，每次最多等待 5 秒，再读取 64 KiB 与 256 KiB 两个样本，每个最多等待 10 秒；慢速网络下最长约 50 秒。服务端只生成随机样本，单响应最多 256 KiB，不读取设备或代理其他地址；响应禁止缓存和压缩。

有效下载速度包含请求及服务响应耗时，取两个可用样本中较慢者；超时的流式样本仅在已收到至少 16 KiB 时参与计算。HTTP 往返显示成功探测的中位数。超时率是本轮 HTTP 探测超时的比例，不是 IP 丢包率；TCP 重传、服务响应和浏览器调度都会影响结果。6 次探测也不足以证明长期稳定性。

失败详情分别列出往返探测和下载样本的超时、HTTP 状态、采样内容校验失败或未获得 HTTP 响应的网络错误。HTTP 401 提示刷新并重新登录；浏览器未提供状态时，页面无法进一步区分断网、代理或证书问题。服务端日志中正常的 204/200 只说明请求已被处理，不能证明响应及时到达浏览器。旧版 1.5 秒探测上限可能把高延迟的可用连接计为超时，不能据此推算真实丢包率或串口上限。

估算采用 8N1（每字节 10 位）、64 B 数据分块、Base64、v2 JSON、WebSocket/TLS 开销，并留出 50% 余量；在现有 9600～921600 预设值中选不超出估算容量的最高档。多数探测失败或样本不足时不给出建议，低于最小档时明确显示低于 9600。8N1 帧说明可参考 [Microchip USART](https://ww1.microchip.com/downloads/en/DeviceDoc/Getting-Started-with-USART-90003216A.pdf)，Base64 编码关系见 [RFC 4648](https://www.rfc-editor.org/rfc/rfc4648.html)。

服务器结果仅代表该页面与服务器之间的短时下行参考，不包含串口所在电脑的上行、USB/驱动、页面处理或完整回环能力。两侧均可评估供比较，但取较低值仍不能代替上行及真实设备验证。已加载页面的本机串口收发不受此参考值限制；网络变化后应手动重测。

公共服务的资源预算也会影响评估：HTTP 429 会明确显示额度或请求频率达到上限，不应当作网络丢包。参考波特率未保证多个远端同时转发及其他连接占用下的可用容量，需结合 [资源限制](RESOURCE_LIMITS.md)。服务器每分钟的 `resource_usage` 汇总日志可查看应用流量和拒绝次数，不包含串口载荷。

### 已直连：P2P 参考

在同一个已授权 PeerConnection 上按需创建独立可靠、有序探测通道。六次轻量往返后，双向各两个 32 KiB 样本，共 128 KiB；每轮最多 20 秒，每页同时一个探测，启动间隔至少 30 秒。只读端也可评估。配置、烧录、定时发送或 RX 补传期间拒绝探测；途中新出现忙状态、失去授权或直连则停止。旧版对端不支持时提示评估失败，串口通道保留，不偷偷改测服务器。

显示本页有效发送、有效接收及往返中位数。每个方向取两个样本中较慢者，参考波特率再取双向较低值，按二进制帧、8N1、64 B 分块及 50% 余量估算。探测流量不进串口、不计 RX/TX；可靠通道上的超时不是 IP 丢包率。短样本和有界发送节奏会影响数值，这不是链路极限容量，也不覆盖 WSS 控制/写许可/补传、设备能力及长期稳定性。

可复现验证：运行当前服务后执行 `node scripts/smoke-network-reference.cjs https://127.0.0.1:12567 .local/network-reference-native.json --screenshots`。流程通过原生 Chrome/WebRTC 和模拟串口验证服务器/P2P 选择、多远端对象、只读评估、串口计数隔离、评估后收发、回退使结果失效和取消。它不替代物理串口、原生 Web Serial 权限或实际异网吞吐测试。
